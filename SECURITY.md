# Security Notes

## Public Registration

Public self-registration creates only `student` accounts. Requests that try to pass `role=admin`, `role=editor`, `role=university_admin`, or any other privileged role are rejected before a user is created.

Privileged demo accounts are created only by the idempotent `seed_demo` management command.

## MAX Secrets

`MAX_BOT_TOKEN` and `MAX_WEBHOOK_SECRET` must be set only in `.env` or the deployment secret store. They are never sent to the frontend and must not be committed.

Required production values:

```env
MAX_API_URL=https://platform-api2.max.ru
MAX_BOT_TOKEN=<real bot token>
MAX_INTEGRATION_MODE=real
MAX_WEBHOOK_SECRET=<random 32+ chars>
MAX_WEBHOOK_URL=https://<public-domain>/api/max/webhook/
MAX_WEBAPP_BASE_URL=https://<public-domain>/
```

## MAX Webhook

Production webhook requests must include `X-Max-Bot-Api-Secret`. The backend compares it with `MAX_WEBHOOK_SECRET` using constant-time comparison and stores MAX update ids in `MaxWebhookEvent`, so duplicate updates are acknowledged without duplicate processing.

Register the webhook after deploying public HTTPS:

```bash
python manage.py register_max_webhook
```

## Local Mock Mode

`MAX_INTEGRATION_MODE=mock` is for deterministic local demos. It simulates delivery and stores notifications with `delivery_status=simulated`; it does not prove production MAX delivery.

## Secret Scan

Before submission, run at least:

```bash
git status --short
git grep -n "MAX_BOT_TOKEN\\|x-max-bot-api-secret\\|Authorization:.*eyJ\\|BEGIN .*PRIVATE KEY" -- . ":(exclude).env.example"
```

`.env`, `node_modules`, SQLite databases, logs, media, and build outputs are ignored by `.gitignore`.

## Known Residual Risks

- The MVP uses JWT access tokens without a fully implemented frontend refresh flow.
- Demo data is synthetic and generated by `seed_demo`.
- Production should set strict `DJANGO_ALLOWED_HOSTS`, `CORS_ALLOWED_ORIGINS`, HTTPS termination, and reverse-proxy security headers.
